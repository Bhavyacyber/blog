Building a Home SOC Lab with Wazuh, Sysmon and Windows 11

Bhavya September 9, 2026
Introduction

Security Operations Centers (SOCs) rely on continuous monitoring, log analysis, threat detection, and incident investigation to identify suspicious activity.

To gain practical experience with these processes, I built a hands-on home SOC lab using Wazuh SIEM, Windows 11, Sysmon, and Kali Linux.

The goal was not simply to install a SIEM, but to understand the complete detection pipeline—from generating controlled activity to collecting telemetry, generating alerts, investigating the event, and mapping the detection to the MITRE ATT&CK framework.

The Goal

The primary objectives of the lab were to:

  • Build a functional SOC monitoring environment.
  • Collect security telemetry from a Windows 11 endpoint.
  • Use Sysmon for detailed process monitoring.
  • Simulate controlled security events from Kali Linux.
  • Detect suspicious PowerShell activity.
  • Monitor Windows Firewall events.
  • Create and test custom Wazuh detection rules.
  • Map detections to MITRE ATT&CK techniques.
  • Experiment with automated threat enrichment.

This provided practical exposure to the type of workflow used by security analysts during threat detection and investigation.

Lab Architecture

The environment consisted of three primary components:

Wazuh Manager

The Wazuh Manager acted as the central SIEM and detection platform.

It received security events from the Windows endpoint, processed the logs using decoders and rules, and generated alerts when matching activity was detected.

Windows 11 Target

The Windows 11 machine acted as the monitored endpoint.

A Wazuh Agent was installed on the system to collect security telemetry and forward it to the Wazuh Manager.

Sysmon was also configured to provide detailed Windows system activity, including process creation events.

Kali Linux

Kali Linux was used as the controlled security testing machine.

It generated lab traffic and security activity that could then be observed from the Windows endpoint and detected by Wazuh.

Detection Pipeline

One of the most important things I learned from this project was that a SIEM is only useful when the complete telemetry pipeline works.

The basic flow was:

Kali Linux → Windows 11 → Wazuh Agent → Wazuh Manager → Decoder → Detection Rule → Alert

For Windows Firewall events, the process was:

Kali Linux traffic → Windows Firewall → Windows Firewall log → Wazuh Agent → Wazuh Manager → Firewall decoder → Detection rule → SOC alert

This allowed me to see how an individual security event becomes an actionable alert inside a SIEM.

Windows Firewall Detection

One of the first successful detections involved Windows Firewall DROP events.

Traffic generated during the controlled lab activity was blocked by the Windows Firewall and recorded in the firewall log.

Wazuh collected this telemetry and processed it using its Windows Firewall decoder and detection rules.

A Level 5 Wazuh alert was successfully generated for the observed TCP DROP activity.

This demonstrated the complete path from endpoint telemetry to a visible SIEM alert.

PowerShell Detection

PowerShell is a legitimate Windows administration tool, but attackers frequently abuse it during post-exploitation activity.

To understand how this type of activity can be detected, I created custom Wazuh rules for suspicious PowerShell behavior.

One of the custom detections focused on encoded PowerShell commands and was mapped to:

MITRE ATT&CK T1059.001 — PowerShell

The custom rule successfully generated a real Wazuh alert during testing.

This was an important distinction in my learning process:

A rule passing Wazuh Logtest demonstrates that the rule can match an event.

A real alert demonstrates that the event successfully traveled through the actual telemetry pipeline and triggered the rule.

Sysmon Process Detection

Sysmon was used to provide detailed Windows process telemetry.

One of the investigations focused on Sysmon Event ID 1, which represents process creation.

This allowed suspicious process activity to be observed with additional information such as the process image and command line.

I also investigated a Wazuh detection associated with suspicious PowerShell activity involving Volume Shadow Copy Service (VSS) and access to the Windows SAM hive.

The purpose of the exercise was to understand how endpoint telemetry can be correlated with known attacker behaviors.

Custom Wazuh Rules

I created and tested custom Wazuh detection rules to improve visibility into specific behaviors.

Examples included:

  • Encoded PowerShell command detection.
  • Suspicious PowerShell temporary executable activity.
  • Suspicious access involving VSS and the Windows SAM hive.

The rules were assigned different severity levels so that potentially more significant activity could receive greater attention during investigation.

This helped me understand how SIEM detection engineering differs from simply collecting logs.

MITRE ATT&CK Mapping

An important part of the project was connecting individual detections to the MITRE ATT&CK framework.

For example:

PowerShell → T1059.001

Mapping detections to ATT&CK provides useful context because it helps analysts understand the adversary behavior represented by an alert.

Rather than treating an alert as an isolated log entry, the detection can be viewed as part of a broader attack technique.

Threat Enrichment

I also developed a Python-based threat enrichment component for the lab.

The idea was to take information from security alerts and enrich relevant indicators using external threat intelligence services.

The project included integrations planned for services such as:

  • VirusTotal
  • AbuseIPDB

I initially tested the enrichment components offline so that the detection pipeline could be developed independently from external API availability.

This helped separate the core detection functionality from optional threat-intelligence enrichment.

What I Learned

Building the lab taught me several practical lessons.

1. Telemetry comes first

A detection rule cannot work if the required telemetry never reaches the SIEM.

Understanding the complete pipeline is therefore essential.

2. Logtest is not the same as a real alert

Testing a rule with Logtest is useful during development, but it does not prove that the production-style event pipeline is working.

Real endpoint telemetry must reach the manager and trigger the rule.

3. Detection engineering requires context

A useful detection should provide enough information for an analyst to understand why the event is suspicious.

4. SIEM engineering is iterative

Building the lab involved testing, troubleshooting decoders and rules, generating controlled events, reviewing alerts, and refining the configuration.

That process was just as valuable as the final detections.

Conclusion

This project gave me practical experience with the fundamental workflow of a Security Operations Center.

Instead of treating cybersecurity as purely theoretical, I was able to build a working environment where I could:

Generate activity → collect telemetry → detect behavior → investigate alerts → map techniques → enrich intelligence

The lab is still a work in progress, and I plan to continue expanding it with additional detections, investigation workflows, and security automation.

For me, the most valuable part of the project has been understanding what happens between a security event occurring on an endpoint and an analyst actually seeing a meaningful alert in a SIEM.

That experience has strengthened my interest in SOC operations, detection engineering, SIEM engineering, and security research.
